# Online Bookstore: deployment guide

Live address: https://online-bookstore-zux7.onrender.com

This is a demo deployment on free tiers. It uses the fake payment gateway and the console mailer, so no real payment or e-mail happens (see section 8).

## 1. Architecture

| Part | What | Notes |
|---|---|---|
| Web service | One Render web service, free plan, built from the `Dockerfile` in the repository root (blueprint: `render.yaml`) | Express serves the API under `/api` and the built React app from the same origin (decision D-02). |
| Database | MongoDB Atlas free cluster (M0), database `bookstore` | Atlas clusters are replica sets, which checkout needs for transactions. |
| TLS | Ends at Render | The app trusts `X-Forwarded-Proto` (`trust proxy` is 1 in production) and `server/src/middleware/httpsRedirect.js` redirects plain HTTP to HTTPS. Render's edge also redirects plain HTTP (the check returned a 301 to the HTTPS address). |
| Monitor | `.github/workflows/uptime.yml` | Section 6. |

## 2. Environment variables (names only)

Set in the Render dashboard. Never commit values.

| Name | Purpose |
|---|---|
| `NODE_ENV` | `production`. Turns on secure cookies, HSTS and the HTTPS redirect, and makes the payment and mail provider names mandatory. |
| `MONGODB_URI` | Atlas connection string (`mongodb+srv://...`) naming the database `bookstore`. |
| `JWT_SECRET`, `CSRF_SECRET` | Signing secrets (generated by Render from `render.yaml`). |
| `PAYMENT_PROVIDER`, `PAYMENT_KEY_SECRET`, `PAYMENT_WEBHOOK_SECRET` | `fake` gateway and its secrets. |
| `MAIL_PROVIDER` | `console`: e-mails are written to the service log. |
| `APP_BASE_URL` | The public https address, used in e-mail links. |
| `RATE_LIMIT_GLOBAL`, `RATE_LIMIT_AUTH` | 300 and 20 requests per 15 minutes per IP. |
| `RATE_LIMIT_ACCOUNT` | Failed login attempts per e-mail address per window (10 on the live site). |
| `TRUST_PROXY_HOPS` | Number of proxy layers in front of the app (1 on Render). |
| `CLIENT_DIST` | Set inside the Docker image. |

## 3. Redeploy

`autoDeploy` is off in `render.yaml`. After merging to the deployed branch, open the service in Render and choose Manual Deploy, then Deploy latest commit. The build runs `npm ci` and `npm run build` inside Docker. Check `/api/health` afterwards.

## 4. Seed the live database

Seeding is run from a laptop against Atlas. Atlas must allow the laptop's IP address (Network Access).

1. Put `MONGODB_URI`, `ADMIN_EMAIL` and `ADMIN_PASSWORD` in the environment of the current shell only, for example from hidden prompts. Do not write them to a file.
2. In `server/`, run `npm run seed:admin` (creates or updates the administrator).
3. Run `NODE_ENV=development npm run seed:demo`. The script refuses to run when `NODE_ENV=production`. It adds 5 categories, 12 books, one seller and one customer.
4. Clear the variables.

The demo accounts `seller@bookstore.local` and `customer@bookstore.local` use the password written in the repository, so they are public and for demonstration only.

## 5. Health check

`GET /api/health` returns `{"status":"ok","db":"up",...}` with status 200, and 503 when the database is down. Render uses it as the service health check.

## 6. Uptime monitor and DEPLOY_URL

`.github/workflows/uptime.yml` runs every 5 minutes (and on demand). It requests `$DEPLOY_URL/api/health` and fails the job unless the answer is 200. The request also keeps the free instance awake.

To turn it on, set the repository variable (Settings, Secrets and variables, Actions, Variables tab) `DEPLOY_URL` to `https://online-bookstore-zux7.onrender.com`, without a trailing slash. Without the variable the job is skipped. GitHub may delay or skip scheduled runs on busy periods, and it disables scheduled workflows after 60 days without repository activity.

## 7. Backup and restore

`server/scripts/backup-db.js` works without the MongoDB tools. Run it with `MONGODB_URI` set in the shell, from `server/`:

```
node scripts/backup-db.js backup  ../backups      # writes ../backups/<timestamp>/<collection>.jsonl.gz and manifest.json
node scripts/backup-db.js verify  <backupDir>     # compares document counts with the manifest
node scripts/backup-db.js restore <backupDir> [dbName]
```

`restore` refuses to write into a database that already has data unless `RESTORE_DROP=1` is set. To rehearse a restore, pass a different `dbName` such as `bookstore_restoretest`. The `backups/` folder is ignored by git. A local rehearsal restored all 13 collections with matching counts; a rehearsal against Atlas has not been done. No schedule exists yet: backups are manual.

## 8. Cold start and known limits

- The free Render instance sleeps after about 15 minutes without traffic. The first request after that takes about 50 seconds. The uptime workflow reduces this but does not remove it.
- Free tiers: shared CPU, a 512 MB class instance and a 512 MB Atlas M0 cluster. Results are specific to this setup.
- The fake gateway never charges anyone and the console mailer delivers nothing, so verification and order e-mails exist only in the service log, with their links.
- The global and `RATE_LIMIT_AUTH` limits are per IP. Failed logins are also limited per e-mail address (`RATE_LIMIT_ACCOUNT=10`); this was observed on the live site after PR #79 (`evidence/live-rate-limit-after-fix.md`, one run from one browser). The forgot-password and resend-verification routes rely on the per-address limiter only, because their success responses are not counted by the account limiter.
